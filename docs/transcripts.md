# Isolated local transcripts (fork T8)

## Scope and delivery status

This is the personal fork's opt-in, best-effort local transcript contract, separate from application/debug logs and the upstream native request logger. It is not an audit system, a lossless capture promise, or an application-level encryption service. The reviewed source baseline is upstream `v8.0.40`, commit `d946c4fba6fc9a5cfbca1f3d85184d62ad2fb683`.

Source and configuration changes are not an operational rollout. The core's four production sources (`types.go`, `store.go`, `frames.go`, and `recovery.go`) implement the storage contract below. Release-specific commands, source/image digests, results, and known baseline failures belong in the feature PR and build provenance, not in this operating guide. No deployment or backup-policy change is implied by the presence of the code. Production enablement remains separately owned and approved.

The canonical fork is `https://github.com/seungwonme/CLIProxyAPI` (`origin`); `https://github.com/router-for-me/CLIProxyAPI` remains `upstream`. Keep module `github.com/router-for-me/CLIProxyAPI/v8` and the existing MIT license/copyright notices. Deployment consumes an immutable fork build and owns configuration/mounts only; do not maintain a second patched source copy in a deployment directory. There is no automatic fork sync, merge, update, or deploy mechanism for this feature.

## Configuration and verified ownership

Add this independent **top-level** section, not under `observability`:

```yaml
transcripts:
  enabled: false
  root: "/transcripts"
  users:
    - env_name: "EXAMPLE_TRANSCRIPT_CLIENT_A"
      user_id: "example-user-a"
    - env_name: "EXAMPLE_TRANSCRIPT_CLIENT_B"
      user_id: "example-user-b"
```

The environment names are synthetic examples, not deployed names or credential values. Provision actual values through the operator's existing secret delivery. A binding refers to an already accepted **client** credential; it does not create an access credential, grant permissions, or refer to an upstream provider credential. Configure native client authentication independently. Do not put credential values in this section, source control, PRs, diagnostic output, or build arguments.

- Disabled is the default. An empty enabled root selects absolute `/transcripts`; a relative root is rejected. This does not mount a host directory automatically.
- `enabled`, `root`, user bindings, and environment values are startup inputs. Restart to change them. The reload hook retains the running transcript settings and warns rather than silently changing ownership or logger selection.
- When enabled, the adapter validates 1–1024 bindings; each `env_name` must be nonempty and unique. Each resolved value is whitespace-trimmed and must be nonempty. Duplicate resolved credentials are rejected, even under different environment names or user IDs.
- `user_id` must be nonempty, have no surrounding whitespace, and be at most 128 bytes. Different credentials may intentionally map to the same stable user ID. Names are exact environment lookups, not shell interpolation.
- The request's principal comes from a successful `sdk/access.Manager.Authenticate` result, not an unverified header or a body-supplied username. The adapter matches a SHA-256 digest of that verified principal to its startup binding. A successful provider with an unmapped principal is skipped and counted; failed authentication does not create a transcript. Providers that return an opaque subject rather than the configured credential need a deliberate binding/coverage review.
- Native derived realtime credentials are observed only after their issuing implementation verifies them; attribution prefers the verified issuer principal. This does not log or authorize the ephemeral credential itself.
- A shared client key identifies one configured user. It cannot distinguish multiple humans, devices, or tenants sharing that key. Use distinct client credentials for distinct ownership. Do not claim identity proof beyond the verified access-provider result.

For rotation, provision a new accepted client key, bind its distinct synthetic environment reference to the same stable user ID, then restart. During an intended overlap, old and new **different** keys may both map to that user. Remove the old key from native access configuration and its binding, and restart again when retiring it. Updating only an environment value or live config file does not rotate an already running adapter. Never reuse one resolved key for two user IDs.

Session extraction uses `sdk/cliproxy/session.ExtractSessionInfo(headers, nil, nil)` before reading the body, preserving native header precedence. Body-only session identities are not inferred by eagerly copying a request. Core `boundedMetadata` stores a length-delimited SHA-256 namespace of user plus session; an absent session uses user plus request ID instead. Per-user directories are separately hashed, so identical client session headers do not merge owners. The stable `user_id` remains in record metadata: hashing paths/session tokens is not anonymization. A session header is correlation, not authentication. Downloads are indexed by request ID, not a separate user-facing session browser.

With this feature disabled, transcript code must perform no body copies, create no transcript files, and reserve no transcript storage. This is a transcript-path guarantee, not a claim that upstream's independently configured native logging allocates nothing. Existing `observability.logs` defaults, including `request-log: false`, remain unchanged. Enabling transcripts bypasses native request logging even if that setting is true; enabling debug logging is not required.

Binding/root/store initialization failure is fail-open for inference: the server emits a generic warning and the stats path reports degradation. The configuration still selects the transcript path, so failure does **not** silently reactivate the native request logger. Check stats after every restart; inference success alone does not prove capture is available.

## Implemented storage, lifecycle, and limits

The stdlib-only core under `internal/transcript/core` owns one asynchronous store worker per server controller. The adapter owns native Gin/config/logging/access/transport integration, including the existing `sdk/httptransport.Decorator`; it does not introduce a replacement HTTP client or transport policy. Native lower-level packages depend on those seams, not on the core or adapter. Production composition imports the adapter only in `internal/api/server.go`.

The following describes inspected implementation, not merely planned storage behavior. Final fault-injection and release acceptance remain incomplete:

| Area | Implemented behavior and interpretation |
| --- | --- |
| Aggregate cap | The adapter selects fixed **10 GiB = 10 × 2^30 bytes**, across all users/sessions in this store. The worker reserves encoded file data/frame metadata plus terminal space before writing, enforcing logical bytes plus outstanding disk reservations against the cap. This is not 10 GiB per user and is not configurable through transcript YAML. Queue-memory accounting is separate. Preexisting foreign files can prevent startup reclamation from reaching the cap; see recovery below. |
| Expiry/record bound | No age/TTL expiry. Capacity or the default 4,096-record index bound triggers whole-request eviction, oldest ended first, never body-prefix trimming. An old request can remain indefinitely when both bounds permit. |
| Admission/backpressure | Defaults are 128 active handles and an 8 MiB queue-byte budget. `Begin` uses bounded admission without taking the worker's index mutex. `Capture` admits/copies chunks of at most 32 KiB and counts a refused tail as loss; it does not wait for disk, a queue drain, or a finalizer. Metadata and encoded frames are bounded separately. Failed admission increments skipped/degraded state; refused captures increment drop counters. |
| On-disk records | Each request uses a random 128-bit filename in a hashed user directory. A versioned magic header precedes length-prefixed JSON frames (maximum payload 128 KiB); byte data is reversible JSON base64. Metadata is first, followed by capture/gap frames and terminal status. An in-progress file has `.open`; successful sealing renames it to `.log`. |
| `ACTIVE` | Request lifecycle remains open. `Open` snapshots the readable committed-frame prefix and status; queued bytes and later appends are not part of that reader. Reopen for a newer snapshot. Readable here means a completed frame append, not a promise of per-chunk fsync or crash durability. |
| `ENDED_COMPLETE` | Requires `End(true)`, no known per-handle loss, and no record failure, followed by terminal-frame append, file sync, close, and rename. This is not a business-success status: a fully observed HTTP error can end normally. It does not certify every protocol hook or power-loss durability. |
| `ENDED_INCOMPLETE` | Published conservatively when end intent arrives, then retained if completion is false, loss/failure is known, or recovery cannot trust a sealed terminal state. Partial readable data remains available where valid. A complete-looking frame still inside `.open` does not override failed sync/close/rename. |
| End publication | The first `End` publishes atomic terminal intent independently of both bounded queues. The worker waits for in-flight captures/queued data and uses 4 KiB reserved terminal space. Handles are never recycled. Post-end callbacks cannot mutate another handle; refused late callbacks count at store level rather than rewriting a sealed per-request status. |
| Readers/eviction | `Open` pins a request under the same mutex that excludes deletion. Eviction selects only retired, unpinned records and releases their logical charge only after successful unlink. No eligible victim means more capture can be refused. Full request IDs and their native trailing-eight aliases resolve through a bounded latest-record index. |
| Crash recovery | Startup scans in bounded directory batches, counts all regular-file sizes, validates owned magic/frames/metadata, and indexes valid readable prefixes. Only valid `.log` records with a terminal frame can retain their sealed state. `.open`, missing-terminal, and corrupt/truncated records are incomplete with approximate end time from file modification time; invalid tails remain charged on disk, not silently repaired into completeness. Unknown regular files count toward logical use but are never indexed for deletion. An overlarge owned inventory or unreclaimable excess rejects store initialization; the adapter reports degraded capture while inference continues, without deleting foreign data. Crash-lost in-memory counters are unrecoverable. |
| Filesystem paths/modes | Root/namespace walking uses directory-relative `os.Root`, no-follow opens, and identity checks. New directories use `0700`, files `0600`; the dedicated root is chmodded to `0700` on creation/open for writing, while unsafe namespace/file modes, symlinks, and nonregular entries are rejected. Downloads recheck root/file identity. This does not establish UID ownership by itself; operator-owned mount permissions still matter. |

A request may be absent because authentication failed, the verified principal was unmapped, admission failed, initialization failed, or an ended record was evicted. A missing request ID is not evidence that no request occurred. Dropped chunks/bytes describe known refused capture, not a reliable count of packets, protocol messages, or secrets. Multiple semantic and wire taps can represent the same bytes in different sections; do not add them as network traffic totals.

`Stop` stops admission without blocking; active handles must still reach their actual `End`. Administrative `Close` waits for the worker to drain/finalize those handles. On supported Unix targets a nonblocking exclusive directory `flock` rejects a second cooperating writer and remains held through recovery and worker shutdown. It is advisory, not protection from arbitrary same-privilege filesystem mutation. Do not share the dedicated root with replicas or other writers.

**Logical is not physical.** The cap bounds the store's charged logical data and reservations, not filesystem allocation units, directory entries, journal/COW overhead, sparse allocation, external hard links, an open unlinked file, snapshots, or backups. Base64 downloads also expand binary representation; a downloaded copy is outside the store cap. Use an independently provisioned volume/quota/free-space alert with headroom when a physical limit is required. Disk-full, fsync, close, rename, and unlink failures must be observable and tested; deleting a directory entry is not proof that physical blocks or snapshots were erased.

## Admin statistics and complete downloads

Both routes remain behind the existing v8 management availability/authentication and remote-access policy:

- `GET /v8/management/observability/transcripts` returns credential-free aggregate stats, with top-level `enabled`, `stats`, `best_effort: true`, and `physical_limit: false`. Core counters cover logical bytes, reservations, limit, active/record counts, dropped chunks/bytes, skipped admission/ownership, failures, and degradation. Stats expose no binding environment names, credential hashes/values, request bodies, or user list. They do not bypass management authentication merely because their response is credential-free.
- `GET /v8/management/observability/logs/requests/:id` uses the adapter text renderer when enabled and the existing request-log handler when disabled. The management request itself is not an inference transcript. v0 routes are unchanged. Admin access is global diagnostic access, not an end-user ownership-filtered API.

The inspected renderer sends a text attachment with `Cache-Control: no-store` and `X-Transcript-State`. It preserves native-style request-info, headers, request-body, response, API request/response, and WebSocket timeline sections, followed by transcript status and dropped counters. Retained UTF-8 chunks are rendered in full; non-UTF-8 chunks are reversible standard base64 under `[BINARY base64]`. Base64 is neither redaction nor encryption. There is no intentional body preview/prefix truncation in a complete download: full retained text and binary bytes are the contract, subject to explicitly reported capture gaps and eviction. The output is diagnostic text, not a replacement wire-protocol replay file.

The renderer marks known dropped-data gaps and invalid/incomplete frames. Check the terminal status/footer, dropped counters, `End approximate`, and `Failure`, not just the HTTP 200 download status or the initial state header. An ACTIVE snapshot can be valid but not final. Crash-lost counters cannot be reconstructed.

Headers/query parameters with credential-sensitive names, URL userinfo/fragments, and sensitive redirect/referrer query values are masked before persistence. Arbitrary error strings are not persisted as diagnostics; `logging.SafeErrorDiagnostic` emits allowlisted failure signals/types. These measures do **not** make a transcript secret-free: request/response/error bodies, ordinary header values, URL paths, tool output, prompts, generated code, and WebSocket payloads can contain personal information and credentials. Unknown custom credential fields need a security review. Treat every transcript and download as sensitive raw data.

### Strict reusable-WebSocket ownership

An upstream read may already be blocked while a session is idle or while its previous request ends. Its arrival time alone cannot establish the next authenticated user's ownership. Codex and XAI snapshot a unique binding token **before** `ReadMessage` and require that exact token still to own the connection/active channel **after** the read. Successful raw capture goes only to that stable owner; a matching sink object or user name without the same token is insufficient. Request cleanup and retries replace/clear tokens without retaining a request context on the reusable session.

If a read started with an owner but completes after ownership changes, payload bytes are not persisted to either the old or new request. Known loss is reported through **only the old sink's `Drop`**, never the new sink; no additional failure or payload event is attributed at this boundary. If the old handle has already ended, its core sink records the refused late drop at store level, not as a retroactive change to the successor or sealed old status. If the read started ownerless, it is never retroactively bound to a newly active user: only an ordinary debug diagnostic with opcode and byte size is emitted, without payload, identity, a sink drop, or a global transcript-loss count.

Consequently, the first response on a reused connection can be delivered by native protocol handling but intentionally omitted from the raw transcript when the read began idle or under the old token. This rule prioritizes no cross-user **raw-capture attribution** over completeness. It does not reroute native protocol traffic, guarantee universal loss accounting, or make semantic taps a lossless substitute. A complete-looking status/zero drop count cannot prove every reusable-connection message was captured; ownerless omissions have no attributable transcript counter. Include these handoff cases in release review.

### Why existing plugin hooks are insufficient

Do not enable plugins to obtain transcript ownership or capture. The isolated adapter uses native seams with plugins disabled. Plugin hooks are trusted in-process extension points, not a universally ordered, lossless transport observer.

| Existing plugin capability | What it can see | Why it cannot alone satisfy this contract |
| --- | --- | --- |
| `RequestInterceptor` before/after credential selection | Execution payload/headers and request correlation; can rewrite/terminate. | Not the original authenticated downstream body or guaranteed final HTTP bytes after provider construction; does not establish verified inbound client ownership. |
| `ResponseInterceptor` | Successful non-streaming execution responses. | Does not cover all failures, streamed bodies, flush/disconnect outcomes, or raw WebSocket traffic. |
| `StreamChunkInterceptor` | Successful execution stream chunks/header initialization; may rewrite. | Logical stream chunks are not a complete downstream/upstream transport lifecycle or binary message transcript. |
| `WebSocketResponseObserver` | Upstream execution WebSocket response events. | No universal downstream input/output, handshake rejection, close/control, or direct/sideband relay coverage. |
| `RequestLifecyclePlugin` / `UsagePlugin` | Async terminal summaries / completed usage. | Summaries do not reconstruct raw bodies; terminal callbacks are not independent persistence reservations or crash recovery. |

Unverified surfaces are release-review items, not assertions of universal protocol coverage. New upstream call sites can bypass existing helpers, so review the hook inventory on every upstream merge rather than relying only on the dependency guard.

## Host security and separately owned deployment

Provision an absolute, persistent mount whose host source is outside the source/build/deployment checkout and whose in-container target matches `/transcripts` (or the configured absolute root). Bind a dedicated service-owned directory/volume; do not put it under `logs`, `auths`, a plugin directory, or an upstream source checkout. Verify actual ownership and `0700` directories/`0600` files on the mounted filesystem; container modes alone do not prove host isolation. Do not share the root with another writer, sync tool, or replica. The precise live host path, service UID, storage quota, restart procedure, and mount configuration are deployment-owned and **not delivered here**.

The verified transcript filesystem targets are Linux and macOS; FreeBSD uses the same native Unix locking implementation but was not exercised here. Windows retains the upstream build and disabled-feature path, but enabling capture returns an explicit unsupported-platform error before filesystem mutation and leaves inference available with degraded stats. A nonblocking exclusive directory lock rejects a second live store on the same root. The worker releases its root descriptors on shutdown; subsequent administrative reads reopen the original directory and verify its identity. Reader pins and total reader descriptors are bounded. Generated file and namespace identities are checked before mutations through directory-relative handles. These checks do not claim atomic protection against a same-UID process replacing paths between a check and a mutation; the service-exclusive `0700` root and single writer are required operational boundaries.

On macOS, enable and verify FileVault for the volume actually holding the data. External volumes, containers/VM storage, and remote disks need their own encryption policy; FileVault on the host boot volume is not proof they are encrypted. Encryption at rest does not protect data from a running unlocked account, a privileged container/process, or an authorized management download. Do not assume the application adds encryption.

Exclude the transcript root from all new application/config backups, automatic sync, Time Machine or other backup jobs as appropriate, and image/build contexts. Confirm exclusions at the actual host, volume, and remote backup destinations before enabling capture. Exclusion does not remove already retained backups or snapshots. APFS/COW snapshots, external backup retention, cloned volumes, exported downloads, and previously uploaded data remain outside the logical cap and require separate operator policy. This work neither deletes old backups nor proves an exclusion has been deployed. Never delete or rewrite existing backup copies as an implicit part of enabling or rolling back capture.

The inspected `.dockerignore` excludes the checkout-relative `transcripts` directory and `.gjc`; it cannot exclude an arbitrary absolute host mount or configure backups. Keep secrets and transcript data outside every build context regardless.

## Rollback

Set `transcripts.enabled: false` in the operator-owned configuration and deliberately restart. This restores the upstream native request-logger selection according to its existing settings; it does not automatically enable native request logging. A hot reload alone is not a rollback. Retain the transcript mount/data, old immutable binary/image pins, and existing backups; rollback is not permission to delete data or backups. The disabled v8 request-ID route returns to the native handler, so existing transcript data may require re-enabling the reviewed version in an isolated, approved diagnostic environment for a later download. Keep mount/backup protection in place while retained data exists. Record rollback health/auth checks separately; this document does not claim a restart or deployment occurred.
